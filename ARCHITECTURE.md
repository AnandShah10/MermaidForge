# Architecture

## Guiding principle

Every subsystem — linter, formatter, complexity analyzer, semantic diff, refactoring, AI context builder — reads and writes through **one intermediate graph model** (`src/core/diagram/types.ts`), produced by **one parser dispatcher** (`src/core/parser/mermaidParser.ts`). Nothing re-parses Mermaid text independently. This is the single most important structural decision in the codebase: it's what lets features agree with each other (the linter's "isolated node" finding is the same isolated-node concept the AI context builder and the refactorer use).

```
Mermaid source
      │
      ▼
detectDiagramType()  ──────────────► DiagramKind
      │
      ▼
parseMermaid()
      │
      ├── flowchart/graph ──► parseFlowchart() ──► FlowchartDiagram (full node/edge/subgraph model)
      │
      └── everything else ──► LightDiagramModel (body lines + frontmatter, no structural model yet)
                                          │
              ┌───────────────────────────┼───────────────────────────┐
              ▼                           ▼                           ▼
          linter                     formatter                  complexity
       (syntax-only for          (whitespace-only for         (reports "unsupported"
        LightDiagramModel)        LightDiagramModel)            for LightDiagramModel)
```

**Graph projection.** `core/diagram/graphProjection.ts` reduces every graph-like model (flowchart, sequence, class, ER, state, mindmap, sankey, requirement, block, architecture, C4) to nodes, edges and groups; semantic diff and complexity analysis both run on that projection, so they work for all of those kinds. Diff compares two diagrams of the *same* kind (mixed kinds are rejected), matches parallel edges in order of appearance, and treats a change to a class's members, an entity's attributes, a requirement's fields and so on as a changed node. Complexity is withheld for sequence diagrams (request/reply pairs are cycles by design) and for kinds with no structure to measure (pie, journey, gantt, timeline, gitGraph, quadrantChart, xychart, packet); the score weights were tuned on flowcharts, so for other kinds treat it as a rough size/connectivity signal. Refactoring and presentation mode are per-kind: rename (flowchart, class, ER, state, sequence), remove-unused (flowchart, class, ER, state, requirement, C4, architecture), extract-into-group (flowchart subgraph, class namespace, C4 Boundary, architecture group) and presentation mode (flowchart, class, ER, state, requirement, C4, architecture, block, mindmap). Rename and remove-unused on class/ER/state share a label-aware scanner (`refactoring/renameIdentifier.ts`: it skips quoted strings, comments, text after `:`, `[..]`/`(..)` shapes and `|labels|` in flowcharts, and member/attribute bodies); extract moves declaration lines rather than copying them. Presentation mode dims SVG elements by the ids Mermaid 11 gives each diagram type (`webviews/media/presentation.ts` lists the patterns; ids carry a per-render prefix that is stripped first, and edge ids are split into two node ids by trying every separator against the known id set); where Mermaid gives edges no usable ids (state, C4) only nodes are dimmed. These id patterns are an observed property of Mermaid's output, not a public API, so `scripts/presentation-smoke.mjs` re-checks them against a real render whenever Mermaid is upgraded. Not covered: presentation for sequence/sankey (no per-node ids), remove-unused for block diagrams (several blocks share a source line), extract for ER/state/requirement/block/mindmap (no grouping construct that preserves meaning), and semantic formatting (whitespace-only outside flowcharts).

Nineteen of Mermaid's diagram kinds now have full structural parsers (`core/parser/{flowchart,sequence,class,er,state,pie,journey,gitGraph,timeline,mindmap,gantt,sankey,quadrant,xychart,packet,requirement,block,architecture,c4}Parser.ts`) powering real linting. pie and journey are Mermaid's two simplest grammars — no arrows, no nesting — so their parsers are correspondingly short, but they still get genuine structural linting rather than just syntax-error detection: pie catches duplicate slice labels and non-positive values (which Mermaid renders but almost always indicate a mistake); journey catches duplicate tasks *within the same section* (task names aren't unique ids in Mermaid's own model — the same label can legitimately recur across sections, so duplicates are checked per-`(section, name)` pair, not globally) and tasks with no actors assigned. gitGraph models commit ancestry (including both parents of a merge commit) and branch structure; `branch X` both creates and checks out the new branch, matching Mermaid's own documented behavior. Most gitGraph structural errors — an unknown branch in `checkout`/`merge`, a duplicate branch name, a duplicate explicit commit id, a `cherry-pick` referencing an unknown commit — are treated as parse-level errors (the same treatment an unclosed flowchart subgraph gets), since they represent genuinely invalid input rather than a style concern; the linter adds one further check on top, flagging a branch that was created but never committed to. timeline follows the same period/section shape as journey — a continuation line (bare `:`) attaches another event to the previous period rather than starting a new one, and duplicate period labels within a section are flagged the same way duplicate journey tasks are. mindmap is structurally different from every other parser in this project — nesting is indentation-driven, not delimiter-driven — and it's the one place a genuinely malformed input (a second "root-level" line, which Mermaid mindmaps don't support) is deliberately *not* treated as a hard parse error: rather than cascading a warning onto every line beneath the mistake, the parser attaches that whole mis-indented subtree under the real root with a single warning, since that's a far more useful recovery than either halting or flooding the Problems panel. gantt is the most syntactically varied grammar of the eleven and is scoped accordingly, on purpose rather than by oversight: the parser records raw start/duration tokens, `excludes` and `weekend`, and `ganttSchedule.ts` interprets them on top (see "gantt dates" below). The eight added last (sankey, quadrantChart, xychart, packet, requirementDiagram, block, architecture, C4) lint as follows: sankey — cycles/self-loops (which Mermaid cannot render), non-positive values, duplicate links; quadrantChart — coordinates outside 0–1, undefined classDef, missing axes/points; xychart — series length vs categories, min ≥ max ranges, no series; packet — overlapping fields and uncovered bits; requirementDiagram — invalid risk/verifymethod/relation values, missing fields, duplicate ids, unknown references; block — unknown link targets, spans wider than the column count, empty groups; architecture — unknown parents/edge ends, non-group parents, nesting cycles; C4 — unknown relation endpoints, unlabelled/self relations, empty boundaries. Unknown C4 macros are warnings; style macros are modelled (see "Styling directives"). Complexity scoring, semantic diff, and refactoring stay "unsupported" for all non-flowchart structural types, deliberately: `ComplexityReport`'s metrics are flowchart-graph concepts, and pie/journey/timeline/mindmap/gantt in particular have no graph structure at all to measure — a "complexity score" for a pie chart or a mindmap isn't a coherent idea, so it's left unsupported rather than a made-up number. Formatting also stays whitespace-only for all ten, for the same reason formatting is conservative everywhere a full round-trip renderer hasn't been written (see `formatFlowchart` vs `normalizeWhitespaceOnly` in `core/formatter/formatter.ts`).

stateDiagram scopes the `[*]` pseudostate: top-level markers are `[*start]` / `[*end]`, each composite state gets `[*start]@Comp` / `[*end]@Comp`, and each concurrent region (a bare `--` line) gets `@Comp#2`, `#3`, ... — all of kind `startOrEnd` with label `[*]`. Because start and end are separate nodes, a start→…→end flow has no spurious cycle.

**gantt dates.** `core/gantt/ganttSchedule.ts` computes a schedule (UTC) for the `dateFormat` tokens it knows (YYYY YY MM M DD D HH H mm m ss s SSS X x; anything else marks the schedule unavailable and the date rules stay silent). Durations ms s m h d w M y (months/years clamp the day, so Jan 31 + 1M = Feb 29), `excludes` (weekends, day names, dates) with Mermaid's stretch rule for duration-based ends, `weekend friday`, `after a b` (latest end), `until id`, and implicit start at the previous task's end. Lint severities follow what real Mermaid does: an invalid start is an error (Mermaid throws "Invalid date"); an invalid end/duration token, a day the month lacks (rolled into the next month) and end-before-start are warnings (Mermaid still renders); an `after` cycle is an error (bars get NaN positions). `scripts/gantt-conformance.mjs` fits real bar x-positions against the computed starts (worst deviation under 0.3px) and checks each severity against actual render behaviour.

**Styling directives.** Requirement and block diagrams model `classDef` / `class a,b name` / `style id css` (requirement also `name:::cls`), quadrant keeps its `classDef`s and point classes, and C4 models `UpdateElementStyle` / `UpdateRelStyle` / `UpdateLayoutConfig` (alias targets plus `$param="value"` pairs). CSS text is stored raw, never interpreted. Lint (`styleUnknownClass`, `styleUnknownTarget` warnings; `styleUnusedClass` information) reflects real behaviour: unknown classes/targets are silent no-ops in Mermaid, except block `style <unknown id>`, which throws and is therefore an error; `UpdateRelStyle` only matches an existing relationship in the written direction. `scripts/styling-conformance.mjs` renders each case with and without the statement and compares computed colours. Remove-unused also cleans `style`/`class` references for requirement diagrams and C4 `Update*Style` calls. Layout hints (`LAYOUT_*`, `direction`) are still accepted but not modelled; block diagrams reject the `id:::cls` shorthand in real Mermaid, so it is not parsed.

This boundary is intentional, not an oversight: building a correct structural parser for every Mermaid grammar (sequence diagrams' actor lifecycles, class diagrams' relationship arrows, state diagrams' composite states, ER diagrams' cardinality notation) is a large, diagram-type-specific effort. Rather than fake partial support, every feature that can't act on a diagram type says so explicitly (`{ supported: false, reason: "..." }`), and the live preview — which delegates rendering to Mermaid.js itself rather than our own model — works for all of them today.

**Extending to a new diagram type** means: add a real structural parser producing a new variant in `ParsedDiagram` (see `FlowchartDiagram` for the shape to imitate), then the linter/complexity/formatter/diff functions gain a new branch. No other code changes — commands, AI context building, and the webview already operate through the dispatcher.

## AI provider architecture

```
src/ai/
  types.ts                    — AIProvider interface, AICapabilities, error types
  providerRegistry.ts         — settings → concrete AIProvider instance
  contextBuilder.ts           — what gets sent to a model, with token budgeting + user-visible disclosure
  service.ts                  — AIService: prompt building → provider call → structured-response parsing → local re-validation
  prompts/prompts.ts          — prompt templates per operation
  providers/
    openaiCompatible/
      openaiCompatibleBase.ts — shared chat/completions + SSE-streaming implementation
      customProvider.ts       — generic OpenAI-compatible endpoint (Mistral, Groq, Together, OpenRouter, LM Studio, ...)
    openai/openaiProvider.ts  — thin config wrapper around openaiCompatibleBase
    azure/azureProvider.ts    — thin config wrapper (deployment-scoped URL, api-key header)
    anthropic/anthropicProvider.ts — native Messages API + its own SSE parsing
    google/googleProvider.ts  — native generateContent API (streaming falls back to one chunk — see code comment)
    ollama/ollamaProvider.ts  — native /api/chat, no credentials, host-configurable
```

**No provider-specific type ever appears outside `src/ai/providers/`.** `AIService` and every command handler talk only to the `AIProvider` interface. Adding a provider means: implement the interface (or configure `OpenAICompatibleProvider` if the service speaks the OpenAI protocol), register it in `providerRegistry.ts`, add its settings to `package.json`. Nothing else changes.

**Structured output is a strong instruction, not a contract.** Providers vary in native JSON-mode support (see `AICapabilities.jsonMode`), so `parseStructuredResponse` in `service.ts` tries strict JSON, then a fenced ` ```json ` block, then a fenced ` ```mermaid ` block with the remaining text as the explanation, and only gives up (explanation-only, empty diagram) if none of those work. Nothing is ever silently applied — see the diff workflow below.

**AI never writes directly to a document.** Every AI operation that proposes a diagram change returns through `src/commands/diffWorkflow.ts`, which opens a real VS Code diff editor (current vs. proposed) and requires an explicit "Apply" before a `WorkspaceEdit` is made. This is enforced structurally — no command has a code path that calls `editor.edit()` with AI output directly.

**Context sent to a provider is minimal and disclosed.** `contextBuilder.ts` only ever includes: the current diagram's source (if `sendSourceContext` is on), locally-computed lint findings, and locally-computed complexity metrics. No other file in the workspace is read for AI purposes by any shipped command. `mermaidForge.ai.sendWorkspaceContext` exists in settings for a future code-aware feature but is not consulted anywhere in the current code — it does nothing yet, on purpose, rather than half-implementing workspace scanning.

## Webview architecture

Four diagram views — `PreviewPanel` instantiated three times with a mode (`preview`: follows the active Mermaid editor; `viewer` and `presentation`: bound to one document and opened in the editor's own column, with Return to code) plus `StudioPanel` — all extend `BaseWebviewPanel`, which owns panel lifecycle (create-or-reveal, disposal, message-listener cleanup). Both load the same browser-side bundle (`dist/webview/previewMain.js`, built by esbuild from `src/webviews/media/previewMain.ts`) which bundles `mermaid` itself — chosen over a CDN `<script>` tag so the extension works fully offline and the CSP never needs to allow remote script sources. Studio adds a second, unbundled inline `<script>` (chat UI + tab switching) that shares the same `vscode` API handle the preview script acquired (`acquireVsCodeApi()` may only be called once per webview).

Message protocol (webview ⇄ host) is a flat `{ type, ...payload }` object; see `WebviewMessage` in `webviewPanel.ts`. Every panel's `onMessage` is a single switch statement — there is no separate message-routing layer, since two panels don't yet justify one.

**Formatting a selection:** `core/formatter/formatRange.ts` formats the whole diagram and takes only the requested lines from the result when the line count is unchanged (all kinds but flowcharts), otherwise reports `scope: 'diagram'`. `runFormatCommand` in `registerCommands.ts` applies it to a `.mmd` document or the Markdown block under the cursor; the same function backs the range-formatting provider.

**Pan/zoom:** the host element sits at the container's top-left with `transform-origin: 0 0`; pan is the diagram's top-left in container pixels, `centerView`/`zoomBy` in `previewMain.ts` keep it centred or anchored.

**Toolbar and comments:** `previewMain.ts` builds the toolbar from `<body data-mode>`; buttons post `{type:'toolbar', action, format}` and the host maps them onto the ordinary commands (`webviews/toolbarActions.ts`), so there is one implementation per feature. The host pushes `{type:'comments', items}`; the webview finds node elements with `findNodeElements` (same id matching as presentation mode) and draws count badges, and lists everything in a popover. Rendering calls `mermaid.parse` first, sets `suppressErrorRendering`, and removes stray Mermaid elements after each render. `tests`: `scripts/ui-smoke.mjs` loads the real HTML templates (real CSP) and bundle in headless Chromium.

**Content Security Policy:** `default-src 'none'`, nonce-gated scripts, `webview.cspSource`-scoped styles, images from `cspSource`, `data:` and `blob:`. No `unsafe-eval`, no remote script sources, no inline scripts without a nonce.

## Export

SVG export serializes the rendered SVG directly. PNG export rasterizes that same SVG inside the webview via `<canvas>` + `Image` (loaded from a `data:` URL with an explicit pixel size taken from the viewBox) + `toDataURL()`; if the export theme differs from the live one the diagram is first re-rendered in an off-screen holder. **PDF export is vector-first**: the webview serializes the SVG with the browser's *computed* styles baked into each element (`serializeWithInlinedStyles` in `previewMain.ts` — this is why the host-side converter needs no CSS engine), then on the extension host `rendering/svg/` converts it: `miniXmlParser` (tolerant XML), `pathDataParser` (all path commands → absolute move/line/cubic/close; quadratics exactly, arcs via the SVG endpoint-to-centre parameterisation), `svgStyle` (transforms, colours, style declarations), `helveticaWidths` (AFM metrics for text-anchor alignment) and `svgToPdf` (shapes, text, marker arrowheads, ExtGState opacity, flattened `foreignObject` labels). `rendering/pdfWriter.ts` wraps the content stream in a single-page PDF (shared `assemblePdf` with an accurate xref; standard Helvetica, not embedded) using only Node's `zlib`. If conversion returns nothing or throws, `exporter.ts` falls back to the older **raster** path: `rendering/png.ts` (minimal PNG decoder) + `buildSinglePageImagePdf` embedding the image as a `DeviceRGB` XObject with an optional `/SMask`. Both paths were checked against `qpdf --check`, `pdftotext` and `pdftoppm`; see `tests/svgToPdf.test.ts`, `tests/pathDataParser.test.ts`, `tests/pdfWriterVector.test.ts`, `tests/pdfWriter.test.ts`, `tests/pngDecoder.test.ts`. Known limits: gradients/filters/clip paths/images/`<use>` are skipped, fonts are Helvetica-only, and Mermaid HTML labels are not re-wrapped.

## Extensibility checklist

Adding each of the following requires touching only the listed location(s), not the rest of the codebase:

- **New AI provider** → `src/ai/providers/<name>/`, register in `providerRegistry.ts`
- **New lint rule** → a new branch in `lintFlowchart()` in `core/linter/linter.ts`, plus a setting in `package.json`
- **New diagram-type structural parser** → new `ParsedDiagram` variant + parser file in `core/parser/`; linter/formatter/complexity/diff gain a branch each
- **New refactoring op** → a function in `core/refactoring/refactoring.ts` returning `RefactorResult | RefactorError`, plus a command in `registerCommands.ts`
- **New export format** → a case in `previewMain.ts`'s `handleExportRequest` (webview side) + `exporter.ts` (host side)

## Not yet implemented (architected, not built)

Every folder that once held a stubbed extension point is now implemented — see the phase-by-phase feature list in README.md and CHANGELOG.md for what exists. The remaining gaps are narrower-scope limitations *within* implemented features (documented at each feature's own boundary — e.g. vector PDF, languages beyond the seven analyzed ones, the dozen or so diagram types without a structural parser) rather than whole missing subsystems. `src/presentation/`, `src/comments/`, and `src/analyzers/` are worth calling out specifically since earlier revisions of this document listed them as stubs:

- `src/analyzers/` — code → Mermaid. `analyzer.ts` defines the `CodeAnalyzer` interface and a generic `CodeGraph` (nodes/edges) intermediate model; `registry.ts` is the single table of languages → analyses (imports / classes / calls / react / express / routes) that both the command and the tests read, so adding a language is one analyzer file plus one registry entry. TypeScript/JavaScript analyzers (`typescript/`: import graph, call graph, class diagram, React component tree, Express routes) are built on `ts.createSourceFile` (syntax-only — no type-checked `ts.Program`, no `tsconfig.json` resolution). The other languages (`python/`, `rust/`, `cpp/`, `java/`, `csharp/`, `go/`) have no bundled parser, so each is a lexical scanner over text that `common/scrubber.ts` (Kotlin, Swift, PHP and Ruby via `scrubberExtra.ts`: nested comments, raw/heredoc strings, PHP inline HTML, Ruby `=begin`/heredocs) has first reduced to same-length source with comments and string literals blanked (offsets stay aligned with the original, so string values such as route paths can still be read from the untouched text); `common/callGraphByName.ts` is the shared name-based call resolver. A subtle point worth knowing: because scrubbing blanks a string literal to spaces, any code that splits argument lists on scrubbed text must decide whether an argument is empty from the *original* text (or keep delimiters — Python uses `keepStringDelimiters`), otherwise a lone `"/path"` argument vanishes; both the Python and Go route analyzers hit exactly this bug during development and have tests for it. The call graph is explicitly the least precise analysis, but it is scope-aware: `common/callGraphByName.ts` resolves a bare call to a same-file function first, then to one in a file the caller imports (`importedFiles`, built from each language's own import/include graph; C++ also pairs `foo.h` with `foo.cpp`), and only then to every function of that name — those fallback edges get `kind: 'ambiguous'`, which `mermaidGenerator.ts` draws as dotted arrows and `runAnalysis` counts in its note. The TypeScript analyzer does its own import resolution (named/aliased/default/namespace imports, `require`, `module.exports`, `export … from` barrels, unique-suffix `@/` aliases) and treats a name imported from an unscanned module as bound-but-unresolved rather than falling back to a same-named function elsewhere. `self`/`this` calls resolve only within the class; `obj.method()` resolves through declared types of parameters, fields and `new Foo()`-style locals (`inferTypes`/`localNames` in `callGraphByName.ts`; the TypeScript analyzer has its own class map with `extends`), and a local that shadows an imported name blocks that edge. TypeScript types are strings (`Repo`, `Repo[]` for iterated collections, `Repo{}` for maps) built by `tstr`/`typeOfExpr`; the name-based languages find collection element types in `inferTypes`. Call results are typed from `DeclaredFn.returns` (first scanned type name in the declared return type) and supertypes come from each language's `supers` map (`implements`/`extends`/bases/`impl Trait for`/structural Go interfaces); `callOn` draws an exact edge when the class defines the method and dotted edges to implementers otherwise, ignoring supertypes outside the scan (`declaredTypes`) and calls that would reach more than 12 targets. Go also follows `pkg.Func()` through imports — behaviors and limits are documented in each analyzer's own module comment and exercised in its tests. On the real repositories in `scripts/realrepo-analyze.mjs`, this cut call-graph edges from 16,716 to 11,951 (−29%) versus plain name matching, with the remaining ~2,900 drawn dotted. Web-route analyzers (Express, Python, Java, C#, Go, Rust) share one shape: find app/router holders, then routes and mounts, then show full paths only when a router has exactly one mount chain. Express, Python and Go additionally bind routers across function boundaries: a call whose callee resolves to a scanned function mounts each router argument onto the matching parameter (a holder scoped to that function, so equal variable names in different functions no longer collide), repeated a few rounds so hand-offs through several functions resolve; functions that `return` a router are used wherever their result is assigned or mounted. Go also reads closure scopes (chi `Route`/`Group` with a `func(r chi.Router)` literal), and resolves import aliases for all of these. Struct/class fields are holders too: Go keys a holder by struct type and field (found from the declared router type, so assignment sites do not matter; an embedded router makes the method receiver the holder) and the TypeScript analyzer by class and member name (`this.router`, `new C().router`). `springFunctional.ts` reads Spring functional endpoints (uppercase verb calls plus `nest`/`path`/Kotlin `"/x".nest {}` prefixes) for Java and Kotlin. TypeScript type strings can carry generic arguments (`Box<Repo>`, plain arguments only; `baseName`/`argsOf`/`subst` in `callGraphAnalyzer.ts`). `loopExpansion.ts` is the small string evaluator Express (and, through a loop environment consulted by `str`/`handlerName`, Fastify/Koa/Hapi) uses to expand `forEach`/`for…of` loops over literal arrays and `readdirSync` directory listings (nothing is executed; anything it cannot evaluate leaves the loop to the ordinary analysis). NestJS, Fastify and Koa live in `nodeFrameworkRoutes.ts`: Nest reads decorators, Fastify treats the first parameter of each `register`ed plugin (and, for `@fastify/autoload`, each plugin file under a literal `dir`) as a holder found by fixpoint over `register` calls, Koa reads `router.routes()` and `koa-mount` mounts, `fp()` wrappers are unwrapped, Nest `RouterModule.register` trees prefix the controllers of each `@Module`, and Hapi `server.route` is read like Fastify's `route`; its graph is merged with the Express graph under one 'Node Web Routes' analysis. Rust adds poem, tide and warp: poem is axum-shaped, tide is a statement-chain on a `tide::new()` variable, and warp has no router at all, so `rustWarpRoutes.ts` evaluates filter expressions (`path!`, `.and` distributing over `.or`, named filters, `-> impl Filter` functions) into one route per alternative, ignoring the closure of extractor filters such as `with_db(db)` so it cannot replace the real handler.

**Real-repository validation.** `scripts/realrepo-analyze.mjs <reposDir>` runs every analysis the registry offers over each repository's files and checks that the output parses with this project's parser and renders in real Mermaid (it needs Playwright + Chromium and is not part of `npm test`; build its bundle with `esbuild .conformance-build/real-entry.ts`). Its first run over 19 repositories found 6 failing diagrams that unit tests on hand-written snippets had not: `"` escaped as `\"` in flowchart labels (Mermaid has no backslash escape — `#quot;` is used now), Rust `impl` blocks for `()`/`&'static [u8]`/`[T; N]` becoming invalid class ids, multi-line `where` clauses leaking into class names, class members containing braces or quotes, and `<` before `(` in a member (`operator<(..)`, `f<R(A)`), which crashes Mermaid's class-diagram parser. `classesToClassDiagram` now gives unsafe ids a safe id plus the original as display label and sanitises members. Comparing route counts with a grep of the source then found the router-through-function-parameter gap in Go (4 of 27 routes found in a gin RealWorld app; 27 of 27 now). `generateFromCodeCommand.ts` is the only VS Code-touching file; `runAnalysis` in the registry is pure and warns on very large graphs.

`src/git/` follows the same split for its one generative feature, git-history-to-timeline: `gitHistoryTimelineGenerator.ts`'s `generateTimelineFromCommits()` is a pure function (plain `{message, date}` commit objects in, Mermaid `timeline` text out) — grouping by year or month, sorting events within a period by actual commit date regardless of input order, capping events per period with a visible "(+N more)" summary rather than an unbounded wall of text, and defending against two real edge cases a naive line-by-line generator would trip over: a commit message containing its own `:` (fine — only the *first* colon on a line is the period/event separator, matching how the parser reads it back) and one containing a literal `%%` (which would otherwise be misread as a Mermaid comment marker by this project's own parser, so it's broken up on generation). `gitHistoryTimelineCommand.ts` is the one vscode-touching piece: it fetches commits via `gitIntegration.ts`'s `getCommitLog()` (the same `Repository.log()` API VS Code's own Source Control view uses — no separate `git` process spawned), capped at 500 commits, and hands plain data to the generator. Generated output is round-tripped through this project's own `timelineParser.ts` in tests to confirm it's genuinely valid Mermaid, not just plausible-looking text.
- `src/presentation/` — `presentationEngine.ts` computes an ordered, cumulative reveal sequence from a `FlowchartDiagram` (author-written `%% step:` comments if present, otherwise one step per node in declaration order), and `webviews/media/presentation.ts` applies it to an already-rendered SVG by toggling a dimming CSS class — deliberately never re-laying out the diagram, since that would defeat the point of a stable presentation. Node dimming matches Mermaid's `flowchart-<id>-<n>` id convention; edge dimming is a best-effort match against Mermaid's `L-<source>-<target>-<n>` edge-path id convention and degrades gracefully (edges simply stop dimming, nodes are unaffected) if a future Mermaid version renames that convention. Both the step engine and the DOM-manipulation logic are unit-tested — the latter with `jsdom`, so the "it dims the right elements" claim is machine-verified, not just asserted in prose.
- `src/comments/` — a local-first comment store, split the same way the Draw.io converter and AI providers are: `commentStore.ts`'s `CommentStore` class holds all the add/update/delete/list logic and is unit-tested against a plain in-memory `CommentDataStore`; `vscodeFileStore.ts`'s `VsCodeCommentFileStore` is the one production implementation, persisting to `.mermaidforge/comments.json` in the workspace root (falling back to session-only in-memory storage when no workspace folder is open, via the same `CommentDataStore` interface — no special-casing needed elsewhere). The `CommentBackend` interface (`types.ts`) is what a future GitHub/GitLab/Azure DevOps-backed implementation would satisfy instead, without any calling code changing. Comments attach to a node, an edge, or a whole diagram, identified by a portable `documentKey` (`documentKey.ts`: workspace-relative path + starting line, so the JSON file stays meaningful across machines and is safe to commit). Studio's Comments tab and the `Mermaid: Add Comment` command are the two entry points, both going through the same `CommentBackend` passed into `CommandContext`.

`src/converters/drawio/` **is** implemented (see above) — parses mxGraph XML (both uncompressed, and Draw.io's default compressed save format via `zlib.inflateRawSync`) by hand-rolled attribute extraction (no XML DOM dependency) into a generic `DrawioGraph`, then `drawioGraphToMermaid()` renders it as a flowchart. It intentionally does not attempt: geometry/layout preservation, swimlanes, or nested groups — see its module comment and README for the exact boundary.

## Testing

`tests/*.test.ts` (vitest) cover every pure `core/` and `ai/service.ts`/`ai/contextBuilder.ts` function — parser (flowchart, sequence, class, ER, state, pie, journey, gitGraph, timeline, mindmap, gantt), formatter (including an idempotency check), linter, complexity, semantic diff, refactoring, AI structured-response parsing (hand-written provider-shaped strings, no network calls), the SVG→PDF converter (XML, path data incl. arcs, styles, shapes, text, markers, opacity), the vector PDF writer, the PNG decoder and PDF writer (round-tripped through real `zlib` and validated against real PDF tooling — see `rendering/pdfExport.ts`'s module comment), the presentation-mode step engine, the comment store (`commentStore.ts`'s add/update/delete/list logic, exercised against a real in-memory `CommentDataStore` — the same split that makes the AI providers and Draw.io converter testable applies here too), all three code analyzers plus the Mermaid generator that renders their output, and the git-history timeline generator (feeding hand-written TS/JS source strings, and hand-written commit lists, straight through `ts.createSourceFile` and `generateTimelineFromCommits()` respectively, then round-tripping every generated Mermaid string back through this project's own parser to confirm it's actually valid — not just "looks like Mermaid"). The Draw.io converter's compressed-format support is tested the same way: a real sample is compressed in the test itself with Node's `deflateRawSync` (the exact inverse of what the parser does with `inflateRawSync`), not a hand-typed blob assumed to be representative. The one exception to "no `vscode`, no browser" is `webviews/media/presentation.ts` — its DOM-manipulation logic (which elements get dimmed) is unit-tested against a real DOM via `jsdom` (`tests/presentationDom.test.ts`, opted into per-file with a `// @vitest-environment jsdom` directive; every other test file stays on the default Node environment) rather than left as an unverified claim. Nothing under `src/commands/`, `src/webviews/previewPanel.ts`/`studioPanel.ts`, `src/comments/vscodeFileStore.ts`, or the provider HTTP implementations is unit-tested — those depend on the `vscode` module or the network and would need `@vscode/test-electron` / mocked HTTP respectively, which was out of scope for this pass. Manual testing via `F5` (Extension Development Host) is the current path for that surface.
