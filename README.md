# MermaidForge — AI Mermaid Studio

MermaidForge is a VS Code extension that turns Mermaid diagramming into a full workspace: live preview, a Prettier-style formatter, a linter that reports into the Problems panel, deterministic complexity analysis, safe refactoring, semantic Git diffing, SVG/PNG export, a workspace-wide diagram navigator — and an AI assistant that can generate, explain, fix, improve, and modify diagrams through **any** of six AI provider backends.

> **Status:** this is a Phase 1 + Phase 3 + partial Phase 4 implementation (see [ARCHITECTURE.md](./ARCHITECTURE.md) for the phase plan). Every feature described below is real and working — including code → Mermaid generation, the last major gap from the original spec. What's left is narrower scope items — see "What's not built yet" below.

## Features

### Works with no AI configured
- **Live preview** (`Mermaid: Open Preview`) — debounced, pan/zoom, click-to-source navigation for flowcharts, error-tolerant (a broken diagram shows a message, never crashes).
- **Formatter** (`Mermaid: Format Document` / `Format Selection`) — flowcharts are re-rendered from the parsed model with normalized spacing and shape delimiters, without changing semantics. Sequence, class, ER, state, requirement, C4, block, gantt, journey and timeline diagrams are re-indented by block nesting (`loop`/`alt`/`else`/`end`, `{ … }` bodies, composite states, `section`s); that pass changes only leading and trailing whitespace — never a character of content or the order of lines, which the tests assert. Everything else (including indentation-sensitive mindmaps) gets trailing-whitespace cleanup only. Supports format-on-save.
- **Linter** — duplicate edges, duplicate-labeled nodes, isolated nodes, empty subgraphs, invalid references, overly long labels — reported as real diagnostics in the Problems panel, configurable per-rule. Sequence, class, ER, state, pie, journey, git-graph, timeline, mindmap, and gantt diagrams all get their own structural checks too (isolated participants/classes/entities/states/branches, unclosed blocks/bodies, duplicate declarations, non-positive pie values, journey tasks missing actors, unknown branch/commit references, duplicate timeline periods, empty/duplicate mindmap labels, gantt tasks starting "after" themselves or an unknown task).
- **Complexity analyzer** (`Mermaid: Analyze Complexity`) — nodes, edges, density, cycles, longest path, fan-in/out, a deterministic 0–10 complexity score, and a plain-language recommendation. Needs a node/edge structure with meaningful cycles, so it is not offered for sequence, pie, journey, timeline, gitGraph, quadrant, xychart or packet diagrams (a sequence's request/reply pairs form cycles by design; the rest have no relationships to measure).
- **Refactoring** — rename an id everywhere (flowchart nodes, class names, ER entities, state ids, sequence participants — label text is left untouched, including inline flowchart edge text `A -- text --> B` and `id>asymmetric]` shape text), remove unused items (flowchart, class, ER, state, requirement, C4, architecture) and extract items into a group (flowchart subgraph, class `namespace`, C4 `Boundary`, architecture `group`, state composite state, block `block:Id … end`). Items are "unused" when they have no relationships; extracting moves declaration lines (for a state: its declarations and the transitions between the selected states) and leaves other relationships where they are. Driven by the parsed model, not blind find/replace. Not offered, by design: **extract for ER, requirement and mindmap** (Mermaid has no grouping syntax for them), and **remove-unused for block** (block diagrams are mostly laid out without edges, so "no relationships" doesn't mean "unused"). Inline edge text is recognised in its spaced form (`-- text -->`); the unspaced `A--text-->B` can't be told from ids and arrows, so an id equal to a word inside it would also be renamed — the editor's preview/undo is the safety net.
- **Semantic diff vs Git HEAD** (`Mermaid: Compare With Git`) — reports added/removed/changed nodes and edges, not just text lines. Works for graph-shaped diagrams and, item by item, for pie, journey, timeline, gitGraph, quadrant, xychart and packet; "Show details" opens the full report.
- **Export** (`Mermaid: Export Diagram`) — SVG (vector), PNG (rasterized in the webview), and PDF (single-page **vector** PDF with real paths and selectable text, falling back to an embedded raster image if conversion fails). Built with a hand-written SVG→PDF converter and PDF writer — no headless-browser dependency. See "What's not built yet" for the PDF limits.
- **Draw.io / diagrams.net → Mermaid converter** (`Mermaid: Convert Draw.io to Mermaid`) — reads a `.drawio`/`.xml` export, either uncompressed or in Draw.io's default compressed save format, recovers shapes and connectors, and generates a Mermaid flowchart you can review before saving. See limits below.
- **Diagram navigator** — an Explorer sidebar tree of every Mermaid diagram in your workspace (`.mmd`/`.mermaid` files and fenced ` ```mermaid ` blocks in Markdown), click to jump to source.
- **Presentation mode** (`Mermaid: Presentation Mode`) — step through a diagram with the rest dimmed, without ever re-laying it out (elements are dimmed via CSS, not removed, so positions stay stable between steps). Flowcharts, class, ER, state, requirement, C4, architecture, block and mindmap diagrams reveal one node per step; **sequence diagrams reveal one message per step and sankey diagrams one link per step**. Steps come from `%% step: A, B | Label` comments if you write any (not for sequence/sankey), otherwise declaration order. Prev/Next buttons, arrow-key/space navigation, Esc or Exit to leave.
- **Diagram comments** (`Mermaid: Add Comment`, or the Comments tab in Studio) — attach a comment to a node, an edge, or the diagram as a whole. Stored locally as a plain JSON file (`.mermaidforge/comments.json` in your workspace root) — commit it to git if your team wants shared comments today, well before any real sync backend exists. See limits below.
- **Code → Mermaid** (`Mermaid: Generate From Code`) — reverse-engineer a codebase into a diagram. Pick a language, then what to draw: an **import/package/include graph**, a **class/type diagram** (members with visibility, inheritance and implements), a **call graph** (name-based, approximate), and — where it applies — a **web-route map**. Languages: **TypeScript/JavaScript** (plus **React component trees** and **Express, Fastify, Koa and NestJS routes**), **Python** (plus **Flask/Quart/FastAPI/Django** routes), **Rust** (plus **actix-web, axum, Rocket, poem, tide, warp** routes), **C/C++**, **Java** (plus **Spring/JAX-RS** routes), **C#** (plus **ASP.NET Core** routes), **Go** (plus **net/http, gin, echo, fiber, chi, gorilla/mux** routes), **Kotlin** (plus **Spring and Ktor** routes), **Swift** (plus **Vapor** routes), **PHP** (plus **Laravel and Symfony `#[Route]`** routes) and **Ruby** (plus **Rails `routes.rb` and Sinatra** routes). Scans a folder you pick (or the whole workspace, capped at 300 files — see limits below) and opens the result as a new, unsaved Mermaid document for you to review. Nothing is written to disk automatically.
- **Git History Timeline** (`Mermaid: Generate Timeline From Git History`) — turns your repository's commit history into a Mermaid `timeline` diagram, grouped by year or month, using the same Git API VS Code's own Source Control view relies on (no separate `git` process spawned). Capped at the 500 most recent commits; opens as a new, unsaved document to review before saving.

### AI Mermaid (needs one provider configured)
- **Generate** a diagram from a natural-language description.
- **Explain**, **improve**, **fix** (syntax errors), and **modify** ("Add Redis caching between the API and database") an existing diagram — the assistant is given the current diagram, not just your prompt.
- **Ask** free-form questions about the current diagram.
- **Review architecture** — deterministic lint/complexity findings plus clearly-labeled AI suggestions (missing auth boundaries, SPOFs, circular deps, etc.) — the AI's output is never presented as fact.
- Every AI change goes through a **VS Code diff view** before anything is written. Nothing is ever silently overwritten.
- **MermaidForge Studio** (`MermaidForge: Open Studio`) — one panel combining the live canvas, an AI chat, live complexity metrics, and live problems, so you're not hopping between panels.

## Supported AI providers

| Provider | Setup |
|---|---|
| OpenAI | `AI Mermaid: Configure Provider` → paste API key |
| Azure OpenAI | Configure `mermaidForge.ai.providers.azure.endpoint` / `.deployment` / `.apiVersion` in settings, then add the key via Configure Provider |
| Anthropic | `AI Mermaid: Configure Provider` → paste API key |
| Google Gemini | `AI Mermaid: Configure Provider` → paste API key |
| Ollama (local) | No key needed — just have `ollama serve` running (default `http://localhost:11434`) |
| Custom (OpenAI-compatible) | Set `mermaidForge.ai.providers.custom.baseUrl` — this covers Mistral, Groq, Together, OpenRouter, LM Studio, and most self-hosted OpenAI-protocol servers |

API keys are stored exclusively in VS Code's `SecretStorage` — never in settings.json, never logged. See **Privacy** below.

All deterministic functionality (preview, format, lint, complexity, refactor, export, navigator, Git diff) works fully with **no AI provider configured at all**.

## Configuration

All settings live under `mermaidForge.*` — see `package.json`'s `contributes.configuration` for the full, documented list (AI provider settings, formatter/linter/preview/export/complexity options). Notably:

- `mermaidForge.ai.sendSourceContext` (default **on**) — required for explain/fix/improve/modify/review; turn off and those commands will tell you why they can't run instead of silently sending nothing useful.
- `mermaidForge.ai.sendWorkspaceContext` (default **off**, currently unused by any shipped command) — reserved for a future code-aware generation feature; no command sends source files today regardless of this setting.
- `mermaidForge.ai.maxContextTokens` — soft budget; oversized diagrams are truncated with a visible marker rather than silently dropped.

## Privacy & security

- API keys: VS Code `SecretStorage` only.
- No workspace file is ever sent to an AI provider by any shipped command — only the current diagram's Mermaid source (when `sendSourceContext` is on) plus locally-computed lint/complexity summaries.
- No telemetry is implemented.
- Ollama is a fully local option if you don't want any external network calls at all.

## What's not built yet

Being direct about the boundary rather than shipping fake buttons:

- **PDF export is vector-first, with documented limits.** The preview's computed styles are inlined, converted to PDF drawing operators (paths, shapes, arrowhead markers, opacity, dashes, transforms) and text in the built-in Helvetica font (selectable, but not the diagram's original font, and widths are estimated from Helvetica metrics). Not carried over: gradients, patterns, filters, clip paths, embedded images, `<use>` elements, mid-path markers, and non-Latin-1 characters (rendered as `?`). Mermaid's HTML labels (`foreignObject`, used by flowcharts and class diagrams) are flattened to single centred lines, so long labels that Mermaid would wrap stay on one line. If the SVG can't be converted at all, export falls back to the older raster PDF (a PNG embedded in a PDF) and tells you so. Verified against `qpdf --check`, `pdftotext` and `pdftoppm` on real Mermaid output (flowchart, sequence, pie, class), not just unit tests; there is no automated test of the webview style-inlining step itself. For lossless output use SVG export.
- **Draw.io import limits** — both the default **compressed** save format and **uncompressed XML** exports are supported (compressed diagrams are decompressed with Node's built-in `zlib.inflateRawSync` — no new dependency needed). Geometry/layout, swimlanes, and grouped shapes beyond simple parent-child membership are not translated — only shape labels and connector source/target/label, which is what a Mermaid flowchart can represent anyway. Multiple pages: only the first is converted, with a note.
- **Code → Mermaid limits.** Every analyzer is deliberately **syntax-only and name-based**: no type checking, no build/classpath/`tsconfig`/`go.mod` resolution, no macro or preprocessor expansion. TypeScript/JavaScript uses the TypeScript compiler API's parser; Python, Rust, C/C++, Java, C#, Go, Kotlin, Swift, PHP and Ruby use a hand-written lexical scanner (comments and strings blanked, then brace/indent matching) because no parser is bundled — so unusual formatting, code generation (Lombok, derive/macros, source generators) and conditional compilation can be misread or missed. **Call graphs are the least precise**, but they use scope: a bare `foo()` goes to a `foo` in the same file, else to one in a file the caller imports (TypeScript/JavaScript follows named, aliased, default, namespace and `require` imports, `module.exports`, barrel re-exports and `@/` path aliases; Python, Rust and C/C++ use their import/include graphs), and only if neither applies to every function of that name — those edges are drawn **dotted** and the command says how many there are. `self.`/`this.` calls resolve within the class, and `obj.method()` resolves when the receiver's type is visible in the same function or class — a typed parameter or field, or a local initialised with `new Foo()` / `Foo()` / `Foo::new()` (TypeScript also follows `extends`); a local or parameter that shadows an imported or same-file function name suppresses that edge. A variable's type also comes from a call result when the callee is a scanned function with a declared return type (`-> Repo`, `*Repo`, `Task<Repo>`, `Promise<Repo>`) or, in TypeScript, one that only returns `new Foo()`; `make().save()` chains work the same way. A receiver typed as an interface, trait, abstract/base class (or, in Go, a structurally satisfied interface) gets **dotted** edges to every scanned implementer or subclass that defines the method — possible targets of dynamic dispatch, dropped when a single call would fan out to more than 12. In TypeScript the inference also covers unions with `null`/`undefined` (`Repo | null`, optional parameters), arrays/sets/maps (`Repo[]`, `Array<Repo>`, `Set<Repo>`, `Map<K, Repo>`, `Record<K, Repo>`) through `for…of`, `forEach`/`map`/`filter` callbacks, indexing and `Map.get`, destructuring (`const { repo } = this`, `({ repo }: Deps)`, `const [a, b] = repos`), interface/type-alias members (`deps.repo.save()`), `as` casts and `new Map<string, Repo>()`; Python, Go, Rust, Java, C# and C++ resolve loop variables over collections declared as `list[Repo]`, `[]*Repo`, `Vec<Repo>`, `List<Repo>`, `Repo[]`. Your own generic classes and interfaces are substituted when their type arguments are plain names (`Box<Repo>` gives `Repo` for `Box<T>`'s fields, `T[]` fields and `T` method returns, also for `new Box<Repo>()`); nested generic arguments, generic functions (`first<T>(xs: T[])`) and `extends Base<Repo>` are not. Not resolved: unions of several classes, nested collections, types that only a type checker could infer, function values and untyped objects (Go is restricted to the same package; `pkg.Func()` follows imports). Go "implements" edges are inferred from method *names* only. **Route maps** follow routers that are constructed in plain sight, **passed to other functions** (`register(app)`, `users.Register(v1.Group("/users"))`, `require('./routes')(app)`, Python `register_routes(app)`; nested hand-offs included), **returned from factory functions** (`app = create_app()`, `NewRouter()`, `makeRouter()`), reached through **aliased imports** (Go and Express), and — for Go — declared in **closures** (`r.Route("/p", func(r chi.Router){..})`). Also followed: Fastify (`register` + prefix, `fastify-plugin` `fp()` wrappers, `@fastify/autoload` with a literal `dir`), Koa (`@koa/router`, `koa-mount`), NestJS (`@Controller`, `setGlobalPrefix`, `RouterModule.register` with children), Hapi (`server.route` with an object or array, plugin objects with `register`, `register({ plugin, routes: { prefix } })` and plugin modules exporting `plugin`), and routers kept in Go struct fields, TypeScript/JavaScript class members, and Python class instances (`self.router = APIRouter(..)`, reached as `self.router` or `api.router`). Still not followed: routes registered in loops are followed only for Express, Fastify, Koa and Hapi (the Node frameworks) and only when the loop is over a literal array (or a top-level `const` array) or over `fs.readdirSync(dir)`, with the prefix and `require(..)` built from the loop variable by string literals, `+`, templates, `path.join`/`basename`/`parse`, `.replace`, `.split(..)[n]`, `.slice` — for a directory scan **every scanned file in that folder is assumed to be loaded** (a heuristic: files outside the scan, or conditionally loaded ones, cannot be known), and any other loop, Python route registration in a `for x in [<literals>]:` loop (one `for` line, up to 50 elements, tuple unpacking allowed) is unrolled the same way by text substitution; Go (`for _, v := range []string{..}`), Rust (`for (p, h) in [(..), ..]`, `.iter()`, `vec![..]`), Java (`List.of`/`Arrays.asList`/`new T[]{..}`), C# (`foreach (var v in new[] {..})`), Kotlin (`listOf(..)`) and PHP (`foreach ([..] as $v)`) route loops are unrolled by text substitution when the iterable is written inline (up to 50 elements, the body must use the variable and look like route registration; adjacent string literals are folded and `"/$v"` interpolation is substituted in Kotlin/PHP) — loops over named collections, struct slices and any loop in Nest, Swift, Ruby or macros are left alone; Rust routers kept in struct fields are followed by field name (`Self { users: Router::new().. }`, `self.users = self.users.route(..)`, `.nest("/p", self.users)`; two structs in one file with the same field name are merged, routers behind trait objects are not). Java and C# have nothing to follow here: their routes come from annotations. Spring functional endpoints (`route().GET(..)`, `route(GET(..), h)`, `nest(path(..), ..)`, Kotlin `router { "/x".nest { GET(..) } }`) are read for literal paths only — one router node per file, predicates other than the path (headers, content types), `RouterFunction` values composed with `.and(other)` and `resources(..)` are ignored. ASP.NET conventional routing (`MapControllerRoute`/`MapDefaultControllerRoute` patterns and defaults) covers controllers without `[Route]`/`[ApiController]`, with literal patterns only; Go factories whose router is not a plain `return <variable>`. A workspace scan is capped at 300 files and the command tells you to narrow the folder rather than truncating silently; graphs over 400 edges are generated but flagged as likely unreadable. The `CodeAnalyzer` interface (`src/analyzers/analyzer.ts`) means a new language or framework is a new analyzer file plus a `registry.ts` entry. Rust routes follow `Router::new()`/`App::new()`/`rocket::build()`/poem `Route::new()`/`tide::new()` chains, `web::scope`/`web::resource`, `nest`/`merge`/`mount`/`configure`, `#[get(..)]`-style handlers, and **warp filters** (`path!`, `.and`/`.or` composition, named filters and `-> impl Filter` functions are evaluated into one route per alternative); `.on(..)` method filters, warp custom filters that add path segments internally, and routers built in loops or macros are not followed. **Kotlin, Swift, PHP and Ruby** (added later, same lexical-scanner approach) have these specific limits. Kotlin: no type resolution (overloads merged, same-named types in different packages conflated), scope functions (`apply`, `let`), `it` receivers and generated code (kapt/KSP, multiplatform `expect`/`actual`) are not followed; Ktor user-defined route helpers other than `authenticate`/`rateLimit`/`param`-style blocks and `install`-added routes are missed. Swift: imports are module-level (SwiftPM `Sources/<Module>/`), not file-level; Vapor builders stored in properties, non-literal path components and non-Vapor servers are not followed. PHP: Doctrine-style `@Route("/x", methods={"GET"})` docblocks are read (other annotations are not), YAML/XML routes, Composer PSR-4 maps, trait-method attribution, facades/containers and `$obj->$method()` are not resolved; non-literal route paths show as `(dynamic)`. Ruby: no `method_missing`/`define_method`/`send`; Rails `draw :file` is followed only when the split file is in the scan, `direct`/`resolve` define URL helpers rather than HTTP routes and are ignored (`shallow` in block and option form, `draw :file` for scanned `config/routes/<file>.rb`, brace blocks, irregular and uncountable plurals and `on: :collection/:member` are; `devise_for` takes its modules from the model's `devise` call when the model is scanned, else assumes database_authenticatable/registerable/recoverable and honours `only`/`skip`/`path`/`controllers`), both branches of an `if` in `routes.rb` are read; Sinatra regex paths, `config.ru` `map`/`run` and Grape/Hanami/Roda are not supported. Other languages are not covered. Verified by unit tests on hand-written snippets, and by `scripts/realrepo-analyze.mjs`, which ran every analysis over about 40 real open-source repositories (express, flask, FastAPI's full-stack template, djangoproject.com, microblog, gin, echo, chi, fiber recipes, echox, a gin RealWorld app, axum, actix examples, Rocket, poem, tide, warp, spring-petclinic and its REST variant, eShop, eShopOnWeb, leveldb, fmt, a React and an Express RealWorld app, vscode-extension-samples, the Fastify demo and todo apps, Ktor's samples, Spring PetClinic (Kotlin), Vapor and its template, Alamofire, Laravel, the Symfony demo, Koel, Sinatra, Mastodon and a Rails RealWorld app, Koa's examples, the NestJS samples and typescript-starter) with no crashes, output accepted by Mermaid's parser and rendered by real Mermaid, and route counts compared with a grep of the source on several of them (e.g. 27/27 routes in the gin RealWorld app, 19/19 in the Express one). That run found and fixed real bugs: an invalid `\"` label escape, impl blocks on non-nominal Rust types, `<` in C++ members crashing Mermaid's class-diagram parser, and the missed hand-off patterns above. It has not been run on very large monorepos, and none of it has been exercised in a live VS Code session.
- **Presentation mode limits** — not available for diagrams with no node/edge structure (pie, journey, gantt, timeline, gitGraph, quadrant, xychart, packet). Mermaid gives sequence messages and sankey links no element ids, so those two are matched by document order and checked against the model (message/link count, sankey node names); if they disagree, presentation refuses with a message instead of dimming the wrong things. In sequence diagrams, notes, loop frames and activation bars are not stepped and stay visible. Edge dimming for the other kinds relies on Mermaid's SVG id naming and degrades gracefully (nodes stay accurate, edges just stop dimming) if a future Mermaid changes it.
- **Diagram comments are local-first, not real-time multiplayer.** They're a JSON file on disk (`.mermaidforge/comments.json`), not a live sync channel — two people editing comments on the same diagram at the same time will each see their own changes until the file is shared (e.g. via git) and re-read. Per-item targeting is offered for every diagram kind, but the targets are whatever the diagram's graph projection yields — flowchart nodes and edges, participants, classes, entities, states, and for pie/journey/timeline/gitGraph/quadrant/xychart/packet their slices, tasks, entries, commits or points. Edges are keyed by their two endpoints, so repeated messages between the same participants share one target. With no workspace folder open, comments still work but only for the current VS Code session — there's nowhere durable to write them.
- **Structural parsing** for diagram types other than flowchart/graph, sequenceDiagram, classDiagram, erDiagram, stateDiagram, pie, journey, gitGraph, timeline, mindmap, and gantt (only types Mermaid adds in future, or an unrecognised header) — these get preview, format-safe pass-through and syntax-level lint only. Nineteen types have real structural parsers and linting: the eleven above plus quadrantChart, requirementDiagram, C4, architecture, block, packet, sankey and xychart (cycles, out-of-range values, bad references, overlaps/gaps, length mismatches and similar — see the rule list in ARCHITECTURE.md). Their parsers are line-oriented and cover the documented syntax; styling directives are modelled for the newer types (requirement/block `classDef`/`class`/`style`, requirement `:::`, quadrant classes, C4 `UpdateElementStyle`/`UpdateRelStyle`/`UpdateLayoutConfig`) with the CSS kept as raw text and the references linted (unknown class or target); layout hints such as C4 `LAYOUT_*` are accepted but not modelled. complexity/diff/refactoring for the ten non-flowchart ones are still "unsupported" on purpose — see "Diagram type support matrix" in ARCHITECTURE.md. gantt interprets dates and durations (see ARCHITECTURE.md: `dateFormat` tokens YYYY YY MM M DD D HH H mm m ss s SSS X x, UTC arithmetic, `excludes`/`weekend`, `after`/`until`), cross-checked against real Mermaid bar positions; other `dateFormat` tokens leave the schedule unavailable and the date lint silent. stateDiagram scopes `[*]` per composite state and per concurrent region (`--`), so start/end markers are distinct nodes and complexity/diff work on state diagrams.
- **CI-mode test runner / CLI** — not implemented; tests currently run via `npm test` inside the extension's own dev environment only.

## Development

```bash
npm install
npm run compile   # type-check (extension host + webview)
npm test          # vitest — 52 tests, no VS Code dependency, no network calls
npm run build     # esbuild bundle → dist/
npm run package   # produces a .vsix via @vscode/vsce
```

Press `F5` in VS Code (with this folder open) to launch an Extension Development Host for manual testing.
